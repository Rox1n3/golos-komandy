# Голос команды — система обратной связи и предложений сотрудников

Решение трека хакатона ГК «Модус Трейд». Работающий MVP: сотрудник выбирает категорию, описывает проблему или предложение (при желании — своё решение и файлы), система регистрирует обращение и по правилам администратора направляет его ответственному. Ответственный фиксирует решение и дальнейшее действие, может запросить уточнение или передать обращение другому. Автор видит статус и итог. Всё сохраняется для аналитики и поиска повторяющихся проблем.

Демо-данные взяты из набора «Демонстрационные обращения сотрудников» (A-001…A-020). Все обращения синтетические, авторы и ответственные — условные роли, а не люди.

## 1. Продуктовая концепция

### Решаемая проблема
Предложения и сообщения о проблемах сейчас теряются в переписке и устных разговорах. Непонятно, кто отвечает за вопрос, в каком он статусе и чем закончился. Одни и те же проблемы всплывают снова, и это никто не замечает.

### Ценность
| Для кого | Что получает |
|---|---|
| Сотрудник | Один понятный канал. Видно, кто взял обращение, на каком оно этапе и чем закончилось, включая мотивированный отказ. |
| Руководитель / ответственный | Очередь «назначено мне» со сроками. Решение и следующий шаг фиксируются в одном месте. Можно передать обращение коллеге или задать вопрос автору. |
| Администратор | Категории и правила маршрутизации без программиста. Резервный ответственный и отметка отсутствия: обращение не теряется, когда человек в отпуске. |
| Руководство компании | Показатели из бизнес-задачи: доля рассмотренных, время до первого ответа, доля с зафиксированным результатом, число реализованных улучшений, повторяющиеся проблемы. |

### Целевые пользователи и роли
| Роль в системе | Кто это в датасете | Что делает |
|---|---|---|
| Сотрудник (`employee`) | Сотрудник закупок, Сотрудник проектирования, Сотрудник бухгалтерии, Менеджер по продажам, Координатор проекта, Руководитель проекта, Сотрудник офиса | Создаёт обращения, отслеживает статус, отвечает на уточнения, оценивает результат |
| Руководитель / ответственный (`reviewer`) | Руководитель закупок, Руководитель направления, Ответственный за номенклатуру, … HR / внутренние коммуникации, Администратор документов (15 условных ролей датасета) и добавленный нами «Специалист по охране труда» | Рассматривает обращения, фиксирует решение и дальнейшее действие, назначает ответственного |
| Администратор системы (`admin`) | Администратор системы | Управляет категориями, правилами маршрутизации, резервом, отсутствиями |

Клиенты компании, NPS и опросы — следующий этап (см. «Запланировано» в разделе 4). В MVP есть внутренний еженедельный пульс как заготовка механики опросов.

### Ключевой сценарий (по ТЗ, п. 2.3)
1. **Выбор категории.** Сотрудник выбирает тип (проблема / предложение / положительный отзыв) и категорию. Сразу видно, кому уйдёт обращение.
2. **Описание.** Текст, необязательное поле «Предлагаемое решение», файлы любого формата.
3. **Регистрация и маршрутизация.** Обращение получает код `A-0NN`. По правилу «категория → ответственный» оно уходит ответственному. Если ответственный не назначен или отсутствует, обращение получает резервный ответственный. Маршрут записывается в историю.
4. **Рассмотрение.** Ответственный меняет статус, фиксирует решение и дальнейшее действие, при необходимости запрашивает уточнение или передаёт обращение коллеге.
5. **Обратная связь автору.** Уведомления о каждом шаге, путь обращения с датами, итог (включая мотивированный отказ), оценка результата.
6. **Анализ.** Сводка по типам, категориям и подразделениям, повторяющиеся проблемы, нагрузка ответственных, выгрузка в Excel.

### Процесс рассмотрения (ТЗ, п. 2.5)
| Вопрос ТЗ | Как устроено |
|---|---|
| Как обращение попадает к ответственному | Правило «категория → ответственный» (страница «Настройки»). Резервный ответственный, если правило пустое или человек отсутствует. Маршрут виден в истории. |
| Как фиксируются статус и результат | Статусы: Новое → На рассмотрении → (Ожидает уточнения) → Принято → В работе → Реализовано / Отклонено / Закрыто. Каждый переход хранит, кто и когда его сделал, и комментарий, если он есть. Итоговые статусы (Реализовано, Отклонено, Закрыто) без текста решения не сохраняются — это проверяет сервер; для отказа этот текст и есть мотивировка. |
| Как автор узнаёт о ходе работы | Уведомления (статус, комментарий, запрос уточнения), блок «Требует внимания» на главной, путь обращения с датами. |
| Как предотвращается потеря обращений | У каждого статуса срок (SLA). Просроченные подсвечиваются и фильтруются. Эскалация: срочные (высокий и критичный приоритет, охрана труда) — сразу после срока, остальные — через 48 ч после срока; один раз в каждом статусе руководитель подразделения (резервный ответственный) получает уведомление «срочно — нужна реакция», ответственному приходит напоминание, в истории появляется шаг «Эскалация руководителю». Отсутствующих ответственных обходит резерв. Отказ без мотивировки невозможен. Автор может один раз вернуть формально закрытое обращение. |
| Как выявляются повторяющиеся проблемы | Блок «Повторяющиеся проблемы» в аналитике: категории и темы (теги) с двумя и более обращениями, со ссылками на коды. При подаче автору показываются похожие обращения (можно поддержать существующее вместо нового), а ответственному — возможные дубликаты, которые он может объединить. |

### Конфиденциальность и доступ (ТЗ, п. 2.6)
| Действие | Сотрудник | Руководитель / ответственный | Администратор |
|---|---|---|---|
| Создавать обращения, прикреплять файлы | ✓ | ✓ | ✓ |
| Видеть ленту обращений и их статусы | ✓ | ✓ | ✓ |
| Комментировать, поддерживать, следить | ✓ | ✓ | ✓ |
| Отвечать на запрос уточнения, оценивать результат | автор | — | — |
| Менять статус, фиксировать решение и дальнейшее действие | — | назначенные ему и своего подразделения; резервный — все | все |
| Передавать другому ответственному, запрашивать уточнение | — | то же | все |
| Доска, аналитика, выгрузка в Excel, ИИ-ассистент | — | ✓ | ✓ |
| Категории, маршрутизация, резерв, отсутствия | — | — | ✓ |
| Видеть автора анонимного обращения | — | — | — |

Права проверяются на сервере: обработка обращения — `canProcess` в `src/lib/db.ts`, доска, аналитика, выгрузка и ИИ-функции руководства — проверка роли, настройки — только администратор. Интерфейс показывает чужое обращение в режиме «только просмотр». Сотруднику с аналитики доступны только общие цифры на главной: доля рассмотренных, реализованные улучшения, время первого ответа, доля в срок.

**Два ИИ-чата с разным доступом к информации.**
| | «ИИ-ассистент» (страница) | «Спросить ИИ» (кнопка внизу экрана) |
|---|---|---|
| Кому доступен | Руководитель / ответственный, администратор. Сотруднику — отказ 403 на сервере, пункта нет в меню | Всем ролям |
| Что знает | Обращения с авторами (кроме анонимных) и ответственными, сроки и просрочки, маршрутизацию, кампании, средние значения пульса (группы меньше 3 человек скрыты) | Только тексты, статусы и итоги обращений — то же, что сотрудник видит в ленте. Без авторов, пульса и аналитики |
| Чего не знает никогда | Автора анонимного обращения: эти данные не передаются в модель | То же |

Остальные ИИ-функции руководства (дайджест, вывод по пульсу, черновик ответа, экспертиза, разбор кампании) тоже закрыты для сотрудника на сервере.

**Анонимная подача (необязательная функция).**
- *Зачем:* снять страх писать о чувствительных вещах.
- *Как работает:* имя автора не отправляется в браузер никому, включая администратора. Автор получает код `GL-XXXX-XXXX`: по нему видно статус и можно переписываться с ответственным.
- *Ограничения:* ответственный не может уточнить детали лично, только через переписку по коду. ИИ предупреждает, если текст выдаёт автора (ФИО, телефон, уникальная роль).

### Проверка полезности
- Показатели из ТЗ (п. 2.7) считаются автоматически на странице «Аналитика»: доля рассмотренных, среднее время до первого ответа, доля с зафиксированным результатом, количество реализованных улучшений.
- Оценка автора 1–5 по каждому закрытому обращению (кроме положительных отзывов).
- Пилот: 1–2 подразделения на 4–6 недель. Сравнить долю обращений с результатом и время первого ответа с текущим процессом. Целевые значения согласовать с компанией: ТЗ требует их отдельного определения.

### Почему такой состав MVP (ТЗ, п. 3.1)
В MVP вошёл сквозной путь обращения из п. 2.3 ТЗ — от выбора категории до результата и анализа — и то, без чего этот путь ненадёжен: защита от потери обращений (п. 2.5), права доступа (п. 2.6) и показатели (п. 2.7). Интеграции, клиентская обратная связь и NPS вынесены в следующие этапы: ТЗ называет приоритетом MVP внутренний процесс сотрудников (п. 2.2) и не требует реализации интеграций (п. 1.2, 3.4). ИИ-функции и кампании — дополнения, от которых основной путь не зависит.

## 3. Техническая концепция

### Архитектура
```
Браузер (React 19, Next.js App Router)
   │  JSON / multipart
   ▼
Next.js Route Handlers  ── /api/feedback, /comments, /attachments, /rate, /follow, /vote
   │                     ── /api/categories, /api/settings, /api/users/:id   (администратор)
   │                     ── /api/stats, /api/export, /api/notifications, /api/track/:code
   │                     ── /api/ai/*  (подсказки, похожие, «Спросить ИИ», ассистент, ответ, экспертиза, дайджест, перевод, речь)
   ▼
Слой данных src/lib/db.ts ── маршрутизация (autoRoute), права (canProcess), SLA и эскалация
   ▼
Хранилище MVP: data/db.json (атомарная запись) + data/uploads/<id> (файлы)
   ▲
src/lib/ai.ts ── OpenAI (необязательно); без ключа или без связи — офлайн-правила
```

### Технологии и почему
| Компонент | Выбор | Причина |
|---|---|---|
| Интерфейс и API | Next.js 15 + React 19 + TypeScript | Один проект для экранов и API, строгие типы между ними, быстрый запуск |
| Стили | Tailwind CSS v4 | Единые токены цвета, светлая и тёмная темы |
| Хранилище MVP | JSON-файл с атомарной записью | Запуск без установки СУБД. Доступ к данным изолирован в `db.ts`, поэтому переход на PostgreSQL не меняет API. |
| ИИ | OpenAI API (необязательно) | Помощник: подсказки, поиск похожих, черновики, сводки. Основной сценарий от него не зависит (см. «Роль ИИ и работа без него»). |

### Данные
`Feedback`: код, тип, категория, приоритет, подразделение, текст, предлагаемое решение, автор (скрыт для анонимных), статус, история переходов, ответственный, дальнейшее действие, решение, комментарии, файлы, голоса, оценка автора. `CategoryDef`: название (рус./каз.), ответственный, активность. `Settings`: резервный ответственный. `User`: роль, подразделение, отметка отсутствия. Типы — `src/lib/types.ts`.

### Безопасность и права
- Права проверяются на сервере в каждом изменяющем запросе: обработка — `canProcess`, настройки — `isAdmin`.
- Анонимность реализована на уровне API: `authorId` анонимного обращения никогда не уходит в браузер (`toView`).
- Файлы хранятся вне публичной папки и отдаются через API с безопасными заголовками: HTML и SVG только скачиваются, не исполняются. Выгрузка CSV защищена от формул-инъекций.
- Ключ ИИ хранится только на сервере (`.env.local`). Анонимные авторы и малые группы пульса скрыты от ассистента.
- ИИ-запросы ограничены по частоте (60 в минуту на пользователя), чтобы скрипт не мог израсходовать платный лимит OpenAI.
- **В MVP нет настоящей аутентификации:** вход — демо-переключатель ролей. В промышленной версии — SSO через Битрикс24 / корпоративный каталог, HTTPS, журнал аудита, резервное копирование.

### Роль ИИ и работа без него
ИИ в проекте — помощник: он подсказывает, но ничего не решает. Категорию, приоритет и подразделение выбирает автор; если он не выбрал их сам, их предлагает подсказка (ИИ или простые правила), а выбранное вручную подсказка не меняет. Статус и итог ставит ответственный, маршрут определяют правила администратора. Платформа полностью работает и без ИИ: если ключа OpenAI нет или к OpenAI нет доступа.

| Что | С ИИ | Без ИИ |
|---|---|---|
| Подача, маршрутизация, статусы и сроки, эскалация, уточнения, уведомления, фильтры, аналитика, настройки | ИИ не используется | Работает полностью |
| Язык интерфейса РУС / ҚАЗ (меню, кнопки, статусы, категории) | ИИ не используется: всё переведено заранее | Работает полностью |
| Подсказка категории и приоритета, кнопка «Улучшить с ИИ», проверка анонимности | Модель OpenAI | Простые правила по ключевым словам |
| Поиск похожих обращений | По смыслу текста | По совпадению слов |
| «Спросить ИИ» | Отвечает своими словами со ссылками на обращения | Показывает список подходящих обращений |
| Черновик ответа автору, ИИ-экспертиза, дайджест, разбор кампании, вывод по пульсу | Модель OpenAI | Шаблоны и упрощённые сводки |
| ИИ-ассистент руководства | Работает | Недоступен, отвечает «ИИ сейчас недоступен» |
| Голосовой ввод | Работает | Недоступен |
| Кнопка «Перевести» в карточке обращения: переводит текст, который написал сотрудник, на язык интерфейса (русский ⇄ казахский) | Работает | Недоступна, текст остаётся на языке автора |

**Если OpenAI не отвечает** (например, на площадке нет доступа к интернету), портал не зависает. Запрос к ИИ ждёт не больше 15 секунд, после сбоя ИИ на 2 минуты отключается, и все функции сразу работают по правилам из таблицы. Проверено: без связи с OpenAI первый ИИ-запрос вернул офлайн-результат примерно за 11 секунд, все следующие — мгновенно, обращения создаются и маршрутизируются без задержек.

**Какие данные уходят в OpenAI:** тексты обращений и вопросы к ассистентам; ассистенту руководства — также условные роли авторов неанонимных обращений и ответственных, сроки и средние значения пульса по отделам; для «ИИ-вывода по пульсу» — средние по отделам и анонимные комментарии; голосовые записи — только для распознавания. Никогда не передаются: авторы анонимных обращений, отдельные оценки пульса и данные отделов, где на пульс ответили меньше 3 человек.

**Как выключить ИИ:** убрать `OPENAI_API_KEY` из `.env.local` и перезапустить сервер.

### Интеграции с корпоративными системами (ТЗ, п. 3.4) — **предложение, в MVP не реализованы**
| Система | Цель | Данные и направление | Способ | Что уточнить до реализации |
|---|---|---|---|---|
| **Битрикс24** | Вход сотрудников, оргструктура для маршрутизации, уведомления там, где люди уже работают | Из Б24: сотрудники, подразделения, руководители, отсутствия (отпуска). В Б24: уведомления в чат и колокольчик о новых обращениях, запросах уточнения, смене статуса. По желанию: задача Б24 для принятого предложения со ссылкой на обращение. | REST API Битрикс24 (входящий вебхук или локальное приложение OAuth 2.0), исходящие события об изменении пользователей | Облачный или коробочный портал; права приложения; кто владеет оргструктурой; нужна ли синхронизация задач в обе стороны |
| **1С УТ** | Контекст для обращений по закупкам, номенклатуре и документам (A-003, A-005, A-007) | Из 1С: справочник номенклатуры, контрагенты (без коммерческих условий), статусы документов. В 1С ничего не пишется. | HTTP-сервисы или OData 1С, только чтение, через промежуточный сервис | Версия конфигурации; какие справочники допустимо показывать; ограничения по персональным и коммерческим данным; нагрузка на базу |

**Как это встроится в текущий код.** Места подключения уже выделены, поэтому интеграция не потребует переделки портала:
- **Уведомления в Битрикс24.** Все уведомления портала (назначение, уточнение, комментарий, смена статуса, эскалация) создаются в одной функции `notify()` в `src/lib/db.ts`. Достаточно добавить в неё вызов модуля отправки в Битрикс24 (сам модуль — запрос к REST API и сопоставление пользователей), и все события сразу пойдут в Б24.
- **Сотрудники, подразделения и отпуска из Битрикс24.** У пользователя портала уже есть подразделение, роль и отметка «отсутствует»; маршрутизация (`autoRoute`) уже передаёт обращение резервному ответственному, если человек отсутствует. Синхронизация будет заполнять эти поля из Б24 вместо ручной отметки администратора; к пользователю добавится только ID в Битрикс24.
- **Ответственные по категориям.** Правило «категория → ответственный» хранит ID пользователя, поэтому после синхронизации администратор будет выбирать ответственных из сотрудников Б24 на той же странице «Настройки».
- **Справочники 1С УТ.** Подключаются только на чтение через отдельный модуль; основной сценарий от них не зависит, они лишь дают контекст (например, карточку номенклатуры к обращению по каталогу).

В MVP вместо интеграций: пользователи и подразделения — в демо-данных (в интерфейсе вход подписан как «Демо-вход»), уведомления — только внутри портала (колокольчик и блок «Требует внимания»).

## 4. Что реализовано, что имитируется, что запланировано

### Реализовано (работает в MVP)
- Подача: типы «Проблема / Предложение / Положительный отзыв», категория с предпросмотром маршрута, поле «Предлагаемое решение», файлы любого формата (до 10 × 25 МБ), черновик сохраняется, анонимная подача с кодом.
- Маршрутизация «категория → ответственный», резервный ответственный, отметка отсутствия, запись маршрута в историю.
- Рассмотрение: 8 статусов, решение и дальнейшее действие, запрос уточнения (ответ автора возвращает обращение на рассмотрение), передача другому ответственному, обязательная мотивировка отказа, объединение дубликатов.
- Сроки по статусам и приоритетам, просрочка, фильтр «Только просроченные», эскалация с уведомлением руководителю подразделения и напоминанием ответственному (запись в истории обращения).
- Уведомления автору, подписчикам и ответственным (назначение, комментарий, уточнение, статус, эскалация).
- Поиск и фильтры: текст, код `A-001`, тип, статус, подразделение, категория, приоритет, срок, «назначены мне». Канбан-доска с перетаскиванием. Выгрузка в Excel (CSV).
- Аналитика: доля рассмотренных, время до первого ответа, доля с результатом, реализованные улучшения, доля закрытых, распределения по типам, категориям, статусам и подразделениям, повторяющиеся проблемы, нагрузка ответственных, динамика по неделям, оценка авторов.
- Администрирование: категории (добавить, отключить, сменить ответственного), резервный ответственный, отсутствия, таблица сроков, матрица прав.
- Интерфейс на русском и казахском, светлая и тёмная темы, адаптивная вёрстка.

### Дополнительно (усиливает основной сценарий, можно отключить)
- **ИИ при подаче** — подсказка категории и приоритета, переформулировка, проверка анонимности, поиск похожих. Решение всегда за человеком: категорию, приоритет и подразделение, выбранные автором вручную, подсказка не меняет.
- **ИИ для ответственного** — черновик ответа автору, экспертиза эффекта и затрат. **ИИ-ассистент** и **дайджест** для руководства.
- **Кампании** (вопрос руководства со сроком), **еженедельный пульс** (заготовка опросов из п. 2.4), **лента «Что изменилось»**, голосовой ввод, кнопка «Перевести» в карточке обращения (перевод текста автора между русским и казахским).
- Основной сценарий от ИИ не зависит. Без ИИ большинство подсказок работает по простым правилам; ассистент руководства, голосовой ввод и кнопка «Перевести» без ИИ недоступны (подробно — «Роль ИИ и работа без него»).

### Имитируется
- Вход и оргструктура (демо-переключатель вместо SSO и Битрикс24).
- Уведомления только внутри портала (вместо чата Битрикс24 и e-mail).
- Интеграции с 1С УТ и Битрикс24 описаны, но не подключены.

### Запланировано (следующие этапы, ТЗ п. 3.6)
| Этап | Содержание |
|---|---|
| MVP (сделано) | Основной сценарий, маршрутизация, статусы и сроки, уведомления в портале, аналитика, администрирование |
| Этап 2 — пилот | SSO и оргструктура из Битрикс24, уведомления в Битрикс24 и e-mail, PostgreSQL, журнал аудита, роли «руководитель подразделения» с видимостью только своего подразделения |
| Этап 3 — расширение | Чтение справочников 1С УТ, задачи Б24 для принятых предложений, опросы и NPS, клиентская обратная связь, публичная подборка «Что изменилось» |
| Требует отдельной проработки | Хранение персональных данных и сроки хранения, требования ИБ к ИИ-сервисам (или локальная модель), нагрузка и резервирование |

### Известные ограничения MVP
- Нет настоящей аутентификации; любой может переключить роль в демо.
- Хранилище в JSON-файле рассчитано на один процесс сервера и демо-объёмы; для работы всей компании нужна СУБД (PostgreSQL — этап 2).
- Сроки (SLA) считаются в календарных часах, без рабочего календаря и праздников.
- Автор не может редактировать отправленный текст: уточнения идут через комментарии, чтобы сохранялась история.
- Без ИИ подсказки заметно проще, а ассистент руководства, голосовой ввод и кнопка «Перевести» недоступны. Кнопки «Надиктовать» и «Перевести» при этом остаются на экране и при нажатии показывают сообщение об ошибке.

### Допущения
- Категории, ответственные, статусы и сроки — условные из датасета и правятся администратором.
- Даты, голоса и часть комментариев добавлены к датасету для демонстрации сроков и аналитики (датасет это разрешает).
- Подразделение обращения выбирает автор (поле «Кому адресовано»); если не выбрал — его предлагает подсказка по тексту. В обращениях датасета подразделение совпадает с подразделением условного ответственного.
- Ответственный «Специалист по охране труда» добавлен для сценария «Опасность на объекте» (в датасете его нет).

## 5. Запуск

Требования: Node.js 20+ (проверено: установка с нуля `npm install` — без ошибок и уязвимостей, сборка, запуск и `npm test` проходят).

```bash
npm install
npm run dev
```

Откройте http://localhost:3000. База `data/db.json` создаётся из демо-данных автоматически при первом запросе.

- `npm run seed` — удалить базу; при следующем запросе она пересоздастся из датасета.
- `npm run build && npm start` — продакшен-сборка. Для демонстрации лучше она: в режиме `npm run dev` каждая страница при первом открытии компилируется несколько секунд.
- Ключ OpenAI не обязателен: без `.env.local` портал полностью работает (см. «Роль ИИ и работа без него»).

### ИИ (необязательно)
Скопируйте `.env.example` в `.env.local` и укажите `OPENAI_API_KEY`. Модели задаются переменными `OPENAI_MODEL`, `OPENAI_MODEL_SMART`, `OPENAI_MODEL_STT`; время ожидания ответа ИИ — `OPENAI_TIMEOUT_MS` (по умолчанию 15000). Без ключа портал полностью работает: подсказки делаются по простым правилам, а ассистент руководства, голосовой ввод и кнопка «Перевести» недоступны (см. «Роль ИИ и работа без него»).

### Тесты
```bash
npm test
```
Запускает оба автотеста подряд. Каждый поднимает отдельный сервер с временной базой (демо-данные в `data/` не меняются) и после проверки всё удаляет. Первый запуск собирает приложение в `.next-test` (1–2 минуты), дальше пересборка только при изменении `src/`.

**`npm run test:core` — основной сценарий ТЗ на датасете (48 проверок, ИИ выключен):**
- демо-данные совпадают с датасетом: 20 обращений, тип, статус и ответственный каждого;
- все 6 проверочных сценариев датасета: подача с файлом; маршрут по категории и к резервному при отсутствии; смена статуса, уточнение и история комментариев; итог и мотивированный отказ; фильтры по подразделению, категории, статусу и сроку; сводка по типам, доля закрытых, время первого ответа;
- права доступа: кто может менять статус, настройки, выгрузку, аналитику; анонимность; нельзя удалить чужой файл;
- эскалация просроченных обращений.

**`npm run test:ai` — оба ИИ-чата и права доступа к ним (42 проверки):**
- кто может пользоваться каждым чатом;
- что другие ИИ-функции руководства закрыты для сотрудника;
- что чаты отвечают по своим данным: ассистент руководства видит пульс, ответственных и просрочки, «Спросить ИИ» — только обращения;
- ответы на русском и казахском;
- что автора анонимного обращения не раскрывает ни один чат, в том числе при попытке «взломать» инструкцию;
- устойчивость к неверным запросам.

Без ключа OpenAI в `test:ai` проверяются только права доступа (26 проверок), содержательные проверки ответов ИИ пропускаются. Для уже запущенного сервера: `npm run test:ai -- --base http://localhost:3000` (создаст там одно тестовое анонимное обращение).
